## Lecture

Our directory now connects filters, results, and details through shared state. Select a resource and refresh the browser. The selection disappears because a new instance of the application starts with `useState(null)`.

Let's make that selection survive a refresh. We'll first move the existing state into a **custom hook**, check that the interface still works, and then add browser storage behind the hook's interface.

### Learning Outcome Guide

*At the end of this class, you should be able to...*

- Extract component state logic into a custom hook.
- Explain the hook's return values and where its state belongs.
- Initialize state from stored JSON using an initializer function.
- Store and clear a selected resource in `sessionStorage`.
- Test persistence without confusing stored data with React state.

### A useful boundary

`App` needs to know which resource is selected and how to select another one. It doesn't need to know the storage key, JSON format, or browser storage methods.

We'll preserve this interface:

```js
const [selectedResource, setSelectedResource] = useSelectedResource();
```

The first value is the current selection. The second is a function accepting a resource object or `null`. We'll use the familiar setter name in App, but this first version won't support React's function-updater form.

A custom hook starts with `use` and composes other hooks. Each call has its own state; extracting a hook doesn't create a shared global store. We will call this hook once, in App, and continue sharing its values through props. See React's [custom hooks guide](https://react.dev/learn/reusing-logic-with-custom-hooks).

### State and storage have different jobs

| Mechanism | Responsibility in our app |
| --- | --- |
| React state | Supplies the current selection for rendering |
| `sessionStorage` | Keeps a serialized copy available after a refresh |
| Custom hook | Coordinates reading, updating, and clearing the selection |

Browser storage keeps strings, so we'll use `JSON.stringify` when writing and `JSON.parse` when reading. `sessionStorage` is scoped to an origin and a browser tab's page session. It survives reloads; it isn't intended as permanent storage. Restored or duplicated tabs can retain or copy a session, so closing and reopening a tab is not a reliable clearing test. See MDN's [`sessionStorage` reference](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage).

### Why and when to use `useEffect()`

Rendering calculates what to display from props and state. React may repeat that calculation, so we shouldn't write to storage or start requests in the component body. `useEffect()` lets us synchronize with something outside React after it commits an update to the UI.

Use an Effect when that synchronization should follow the component appearing or its props/state changing. For our selection, an Effect can keep `sessionStorage` up to date whenever `selectedResource` changes. Calculations such as filtering resources can happen during rendering; work tied to a specific click can stay in its event handler.

Today we'll save through our update function; Lesson 16 will switch to an Effect. See React's [synchronizing with Effects guide](https://react.dev/learn/synchronizing-with-effects).

1. **Read the saved selection when the state is initialized.**

    Back in the hook, add a storage key and replace the `null` initial value with an initializer function.

    ```diff lang="js" title="src/hooks/useSelectedResource.js"
      import { useState } from 'react';

    + const STORAGE_KEY = 'selectedResource';
    +
      export function useSelectedResource() {
    -   const [selectedResource, setSelectedResource] = useState(null);
    +   const [selectedResource, setSelectedResource] = useState(() => {
    +     try {
    +       const stored = sessionStorage.getItem(STORAGE_KEY);
    +       if (stored === null) return null;
    +       const resource = JSON.parse(stored);
    +       return resource && typeof resource.id === 'string'
    +         && typeof resource.title === 'string' ? resource : null;
    +     } catch {
    +       return null;
    +     }
    +   });

        return [selectedResource, setSelectedResource];
      }
    ```

    We pass a function instead of calling it ourselves. React uses it when initializing this instance's state, rather than rereading storage on every update. This is **lazy initialization**. Development Strict Mode can call an initializer twice to check it, so this function only reads and returns a value; it doesn't write to storage. See [avoiding recreated initial state](https://react.dev/reference/react/useState#avoiding-recreating-the-initial-state).

    The `try` block covers both storage access and JSON parsing. The small shape check rejects values such as a saved number or an unrelated object. This isn't a full data validator; our app is saving its own resource objects.

    If there is no saved value, the selection still starts as `null`. We need to write something before a refresh can restore it.

1. **Save selections through the hook's update function.**

    Add a function before the hook's return statement. It will update React state and attempt to save the supplied value.

    ```diff lang="js" title="src/hooks/useSelectedResource.js"
    -   return [selectedResource, setSelectedResource];
    +   function updateSelectedResource(resource) {
    +     setSelectedResource(resource);
    +     try {
    +       if (resource === null) {
    +         sessionStorage.removeItem(STORAGE_KEY);
    +       } else {
    +         sessionStorage.setItem(STORAGE_KEY, JSON.stringify(resource));
    +       }
    +     } catch (error) {
    +       console.warn('Selection could not be saved for this tab.', error);
    +     }
    +   }
    +
    +   return [selectedResource, updateSelectedResource];
      }
    ```

    App still calls its second returned value `setSelectedResource`. It now receives our wrapper function instead of React's setter directly. No change is needed in Results or Details.

    Select a resource and refresh. Its details and highlight should return. In DevTools, inspect Session Storage for the frontend's origin. The `selectedResource` key should contain JSON for the selected resource.

    If storage is unavailable, selecting still updates the interface for the current visit. The console warning explains why persistence didn't succeed.

### What we've accomplished

App still owns the selection through its hook call. The hook now hides the storage details behind a small interface, while Results and Details continue to receive props.

Writing to storage from an event-triggered update function is valid. In Lesson 16, we'll explore a different requirement: keeping storage synchronized whenever selection state changes, using an Effect. That will also let us return React's setter directly.

For now, we store a snapshot of the entire resource. If the original data changes, that snapshot can become stale. Storing only an id is a useful next design to consider.
