## Lecture

In Lesson 15, our custom hook saved a selection whenever we called its update function. Now we'll explore how React can synchronize an external system with state after a render is committed.

We'll use that idea twice: keep browser storage synchronized with the selected resource, and load resource data from our backend. Both involve work outside the calculation of JSX. React calls this kind of synchronization an **Effect**.

### Learning Outcome Guide

*At the end of this class, you should be able to...*

- Distinguish rendering, committing UI updates, and running Effects.
- Use `useEffect` to synchronize state with an external system.
- Explain dependency arrays and the cleanup function.
- Fetch resource data through a custom hook with loading, error, and retry states.
- Prevent an obsolete request from overwriting a newer request's state.

### Why and when to use `useEffect()`

`useEffect()` lets us keep a component synchronized with something outside React, such as browser storage or a server. React may render a component repeatedly, so rendering should only calculate the UI. The Effect's callback runs after React commits the update, keeping storage writes and requests out of that calculation.

Use an Effect when the work should follow the component appearing or a dependency changing. Here, storage follows `selectedResource`; fetching starts when the component using our hook mounts and repeats when `requestVersion` changes for a retry.

We don't need an Effect to filter resources from existing state; we can calculate that during rendering. Work caused by one action, such as submitting a form, belongs in that event handler. Being asynchronous doesn't, by itself, mean that `fetch()` needs an Effect.

### A practical lifecycle model

React calls our component to calculate the UI: **render**. It applies the necessary DOM changes: **commit**. An Effect then performs its synchronization work. When dependencies change, React runs the previous cleanup before the next setup. Cleanup also runs when the component is removed.

| Dependency argument | When setup runs |
| --- | --- |
| Omitted | After every commit for the component |
| `[]` | On mounting, with no dependency-driven reruns |
| `[selectedResource]` | On mounting and after that value changes |

Dependencies must include the reactive values used by the Effect. They aren't an arbitrary schedule to choose for convenience. React's [`useEffect` reference](https://react.dev/reference/react/useEffect) describes setup, dependencies, and cleanup.

<Aside title="Keep Strict Mode enabled">
The starter uses Strict Mode. During development, React runs an extra setup/cleanup cycle when checking Effects. You may see an aborted request followed by a successful one. Correct cleanup makes that safe; removing Strict Mode would hide the check.
</Aside>

1. **Create a hook for loading resources.**

    Add `src/hooks/useResources.js`. Read the request from top to bottom before using the hook.

    ```js title="src/hooks/useResources.js"
    import { useEffect, useState } from 'react';

    const API_BASE_URL = 'http://localhost:3000';

    export function useResources() {
      const [resources, setResources] = useState([]);
      const [isLoading, setIsLoading] = useState(true);
      const [error, setError] = useState(null);
      const [requestVersion, setRequestVersion] = useState(0);

      useEffect(() => {
        const controller = new AbortController();
        const { signal } = controller;

        async function fetchResources() {
          try {
            const response = await fetch(`${API_BASE_URL}/resources`, { signal });
            if (!response.ok) {
              throw new Error(`Request failed: ${response.status} ${response.statusText}`);
            }
            const data = await response.json();
            if (!Array.isArray(data)) {
              throw new Error('Expected an array of resources.');
            }
            if (!signal.aborted) setResources(data);
          } catch (err) {
            if (!signal.aborted) setError(err);
          } finally {
            if (!signal.aborted) setIsLoading(false);
          }
        }

        fetchResources();
        return () => controller.abort();
      }, [requestVersion]);

      function refetch() {
        setIsLoading(true);
        setError(null);
        setRequestVersion((version) => version + 1);
      }

      return { resources, isLoading, error, refetch };
    }
    ```

    The hook starts in a loading state. A successful response supplies an array; a failed request supplies an error. `fetch` doesn't reject merely because the server returns an HTTP error status, so we check `response.ok` ourselves.

    The Effect owns each request and its controller. Cleanup aborts that request when the hook unmounts or another request version replaces it. Checking the signal before **every** completion update prevents an obsolete request from changing the resources, error, or loading state.

    `refetch` clears the error, shows loading, and changes a dependency. React then cleans up the previous Effect and starts a fresh request. Retry requests get the same cleanup as the first request.

    Notice that the Effect callback itself isn't `async`. It must return a cleanup function, not a Promise. The asynchronous work lives in the inner function.

### What we've accomplished

Our two hooks now have distinct jobs. `useSelectedResource` synchronizes selection with storage. `useResources` manages an asynchronous read and exposes enough state for the UI to explain what's happening.

The saved selection is still a resource snapshot. Fetching a new list doesn't automatically update that saved object. Consider how storing an id and looking up the current object would change this design.
