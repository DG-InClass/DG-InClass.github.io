## Lesson Focus

This lesson introduces automated testing as a developer feedback tool. Keep the examples small and concrete: pure JavaScript functions are easier to test than browser pages, and they let students focus on test structure before adding DOM complexity.

Use this demo to show:

- automated testing as repeatable evidence that code still behaves as expected
- the difference between unit, integration, end-to-end, and manual exploratory testing
- Vitest project setup and scripts
- the anatomy of a test file: imports, `describe`, `it` or `test`, and `expect`
- the Arrange-Act-Assert pattern
- the red-green-refactor TDD loop
- failure messages as debugging information
- watch mode for quick feedback
- coverage as a clue about what ran, not proof that the code is correct

Put in other words, we must identify our **inputs** and our **outputs**. Everything in between are the *functions* that achieve our final results. ### Our Plan

We will create tests for two modules: `formatter.js` and `cart.js`. We'll need some rules and expectations.

The `formatter.js` will export a couple of functions (`formatCurrency` and `pluralizeItem`) that help us format information for text output. With regard to the formatters, we can say

- it formats money for Canadian English readers
- it uses the singular word item for a count of 1
- it uses the plural word items for any other count

The `cart-calculator.js` will export a single function: `calculateCartTotal`. With regard to this cart calculator,

- it calculates a line total
- it calculates a total from several items
- it applies a percentage discount
- it throws a useful error for an invalid discount rate

    <Aside type="tip" title="test vs. it">
    I prefer to use the `it()` function over the `test()` function, largely because of two reasons:
    
    - I want to maintain a **specification mentality** instead of a testing mentality.
    - It just simply reads nicer when you look at the code.

    Most people think of "testing" as something they do *after* building something. On the other hand, people think of "specifying" as something they do *before* building something.
    </Aside>

1. When you look at the output, you should see the tests listed as "skipped" items.

    As we move through building each test, we'll remove its `.todo` so that it's a real unit test. In the meantime, that "todo" list of tests helps you to work in small chunks. It also makes it easier to pause your work for a break or the end of the day and still "pick up" where you left off. 🎉

1. We'll start our first test by following the "Triple-A" pattern: Arrange, Act, Assert.

    ```diff lang="js" title="tests/formatters.spec.js"

    +   it('formats money for Canadian English readers', () => {
    +     // Arrange
    +     // Act
    +     // Assert
        });
    ```

    Notice that an "empty" test passes. That's *not good*. **We want a *failing* test** to start with. It's part of the "Red-Green-Refactor" rythm that a good software developer should build.

1. Let's do the Arrange and Act portions of our first test.

    ```diff lang="js" title="tests/formatters.spec.js"
        it('formats money for Canadian English readers', () => {
          // Arrange
    +     const amount = 12.5;

          // Act
    +     const result = formatCurrency(amount);

          // Assert
        });
    ```

    🎉 HORRAY! It's broken! Let's fix it. 👀

1. Create the `formatter.js` file and export **a *minimal* version** of the function we need. In this case, it's just a "stub".

    ```diff lang="js" title="src/formatter.js"
    + export function formatCurrency() {
    + }
    ```

    We'll also need to import it in our specification file.

    ```diff lang="js" title="tests/formatters.spec.js"
      import { describe, expect, it } from 'vitest';
    + import { formatCurrency } from '../src/formatters';
    ```

1. Our test passes, but we're not done. Now we need to **define our expectations**. Let's fill in the "Assert" section.

    ```diff lang="js" title="tests/formatters.spec.js"
        it('formats money for Canadian English readers', () => {
          // Arrange
          const amount = 12.5;

          // Act
          const result = formatCurrency(amount);

          // Assert
    +     expect(result).toBe('$12.50');
        });
    ```

    Once again, our tests fail. 🎉

1. Let's edit our function to make the test pass.

    ```diff lang="js" title="src/formatter.js"
    - export function formatCurrency() {}
    + export function formatCurrency(amount) {
        return `$${amount.toFixed(2)}`;
      }
    ```

1. You've just had your first experience of **Test-Driven Development**. By writing our automated tests first, we build our *technical specifications*.

    <Aside type="tip" title="WHY?">
    Why should we follow this? One major reason: **To build *confidence* in our code.**
    
    There's another good reason: This is the point in which we are **thinking the hardest**. The point in time when we a) build our tests before our code and b) write the code to make our tests pass is when we are "in the weeds" of software development. If we "get it right" now, and check all our assumptions, then we make it easier to move on to other parts of our program.
    </Aside>
</Steps>

💫 These first few steps of setting up our unit tests and then getting the first one to pass is how we build a *cadence* of work. As you practice this discipline 👀, writing unit tests and getting them to pass can be done in a matter of minutes. That's the "Red-Green" part. Where you really get the **quality** is when you spend some more time on the "Refactor" stage. Early on, you won't need to do much refactoring. But, as your code base grows, having these tests in place will help you **refactor with *confidence***. If any of your refactoring attempts "breaks" things, you'll know immediately because of failing tests. 🚀

    +     const counts = [0, 2, 10];

    +     const labels = counts.map(pluralizeItem);

<summary>Sample Refactoring</summary>

```js title="src/cart-calculator.js"
function calculateCartTotal(item) {
  return item.price * item.quantity;
}

function calculateSubtotal(items) {
  return items.reduce((total, item) => total + calculateCartTotal(item), 0);
}

function applyDiscount(subtotal, discountRate = 0) {
  return subtotal - subtotal * discountRate;
}

export function calculateCartTotal(items, discountRate = 0) {
  if (discountRate < 0 || discountRate > 1) {
    throw new RangeError('Discount rate must be between 0 and 1.');
  }

  const subtotal = calculateSubtotal(items);
  return applyDiscount(subtotal, discountRate);
}
```

## Conclusion

Automated tests are code that checks other code. A unit test checks one small unit in isolation, usually a function or module. Integration tests check whether multiple pieces work together. End-to-end tests check a user-like workflow through a running application. Manual exploratory testing still matters because humans notice confusing behavior that a scripted test may not describe.

Vitest test names should describe behavior, not implementation. Prefer test names like "throws for an invalid discount rate" over "calls applyDiscount." Students should learn that a useful failure message points to a specific expectation.

The TDD loop is:

1. Red: write a failing test that describes the behavior you want.
1. Green: write the simplest code that makes the test pass.
1. Refactor: improve the code while keeping the tests passing.

Coverage reports show which lines, branches, and functions executed during the test run. High coverage can still miss important cases if the expectations are weak, so coverage is a prompt for better questions rather than a final grade for quality.
