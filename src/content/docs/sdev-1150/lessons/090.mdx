## Lecture

We're going to split JavaScript code across multiple files and connect those files with ES Module syntax. Students have already written functions, objects, constructor functions, and arrays. Today, the new idea is that those pieces do not all need to live in the same file.

The main habit to build is deciding what a file shares with the outside world. A value or function is private to its module until it is exported. Another file cannot use it until it imports it.

We'll also add JSDoc comments to show how documentation can improve the editor experience. Students should notice that comments are not only for people reading the file later. Well-structured JSDoc comments can also help VS Code provide better hints while they are writing code.

### Named Exports and Named Imports

The `utils.js` file has two local values and then exports them at the bottom of the file.

<Steps>
1. Inspect the `utils.js` file.

    ```js title="~/inclass/09/utils.js"
    function add(a, b) {
        return a + b;
    }

    let info = 'Utility Functions';

    let about = {
        name: info
    }

    export { add, about }
    ```

    The `export { add, about }` statement makes those two names available to other modules.

    <Aside type="note" title="Named Exports">
      This is a named export.

      The exporting file chooses the names it shares. The importing file asks for those same names inside curly braces.
    </Aside>

1. Import these items into `demo.js`.

    ```diff lang="js" title="~/inclass/09/demo.js"
      import { displayHeading } from './display.js';
    + import { add, about } from './utils.js';

      displayHeading('Lesson 09 demo.js has loaded', '=');
      console.log('\t🎵 Code is spread across multiple files');
      console.log();
    ```

    This does not change the behaviour. It just keeps the import easier to read.

1. Let's use the imported items.

    ```diff lang="js" title="~/inclass/09/demo.js"
      console.log();
    +
    + console.log(`Module name: ${about.name}`);
    + console.log(`2 + 3 = ${add(2, 3)}`);
    + console.log();
    ```

    The `demo.js` file can call `add()` and read `about.name` because both names were exported from `utils.js` and imported into `demo.js`.
</Steps>

### Module Scope

Modules have their own scope. A variable can exist inside a module without becoming available everywhere else.

<Steps>
1. Point students back to the `info` variable in `utils.js`.

    ```js title="~/inclass/09/utils.js"
    let info = 'Utility Functions';
    ```

    This value is used to build the `about` object, but `info` itself is not exported.

1. Discuss what would happen if `demo.js` tried to import and use `info` directly.

    ```diff lang="js" title="~/inclass/09/demo.js"
      console.log();
    + // You cannot import items that are not exported
    + import { info } from './utils.js';
    + console.log(info);
    ```

    We do not need to add this line permanently. The important idea is that `info` belongs to `utils.js`. Since `utils.js` did not export `info`, `demo.js` does not have access to that name.

    <Aside type="caution" title="Export Only What Other Files Need">
      Avoid exporting every variable just because it exists.

      A module can keep helper values private and export only the functions, objects, or constants that other files should use.
    </Aside>
1. Because this crashes our program, either remove or comment out these two lines.

    ```diff lang="js" title="~/inclass/09/demo.js"
      console.log();
    + // You cannot import items that are not exported
    - import { info } from './utils.js';
    - console.log(info);
    + // import { info } from './utils.js';
    + // console.log(info);
    ```

    <Aside type="tip" title="Where to put Imports?">
      Give the general advice to always put imports at the top of a file. It's helpful information whenever you return to an older script you haven't seen in a while!
    </Aside>
</Steps>

### JSDoc for Utility Functions

JSDoc comments describe the shape of a value or function. VS Code can use those comments to show parameter names, expected types, and return information.

<Steps>
1. Add a JSDoc comment above the `add()` function.

    ```diff lang="js" title="~/inclass/09/utils.js"
    + /**
    +  * Adds two numbers together.
    +  * @param {number} a The first number.
    +  * @param {number} b The second number.
    +  * @returns {number} The sum of both numbers.
    +  */
      function add(a, b) {
          return a + b;
      }
    ```

    After adding this comment, hover over `add` in `demo.js`. VS Code should show a more useful description.

1. Add a JSDoc comment for the exported `about` object.

    ```diff lang="js" title="~/inclass/09/utils.js"
      let info = 'Utility Functions';

    + /**
    +  * Information about this utility module.
    +  * @type {{ name: string }}
    +  */
      let about = {
          name: info
      }
    ```

    <Aside type="note" title="JSDoc and Runtime Behaviour">
      JSDoc comments help people and tools understand the code.

      They do not change what JavaScript does when the program runs. The `add()` function still works the same way; the editor simply has more information about it.
    </Aside>
</Steps>

    Hover over `Shape`, `assignDimensions`, and `area` in VS Code. The JSDoc comments in `shapes.js` should help explain those values even though we are using them in `demo.js`.

1. Create a square and a triangle.

    ```diff lang="js" title="~/inclass/09/demo.js"
      let circle = new Shape('circle');
      circle.assignDimensions({ radius: 5 });

      console.log(`Circle area: ${circle.area().toFixed(2)}`);
    +
    + let square = new Shape('square');
    + square.assignDimensions({ length: 8 });
    + console.log(`Square area: ${square.area().toFixed(2)}`);
    +
    + let triangle = new Shape('triangle');
    + triangle.assignDimensions({ base: 10, height: 6 });
    + console.log(`Triangle area: ${triangle.area().toFixed(2)}`);
    + console.log();
    ```

    The constructor and methods are defined in `shapes.js`, but the objects are created and used in `demo.js`.

1. Try a capitalized shape type.

    ```diff lang="js" title="~/inclass/09/demo.js"
      let triangle = new Shape('triangle');
      triangle.assignDimensions({ base: 10, height: 6 });
      console.log(`Triangle area: ${triangle.area().toFixed(2)}`);
      console.log();
    +
    + let capitalTriangle = new Shape('Triangle');
    + capitalTriangle.assignDimensions({ base: 12, height: 5 });
    +
    + console.log(`Capital triangle area: ${capitalTriangle.area()}`);
    + console.log();
    ```

    This looks like it should work, but it does not. The supported shape is `'triangle'` with a lowercase `t`, and the constructor stored `'Triangle'` exactly as it was typed.

    <Aside type="note" title="Case-Sensitive Strings">
      JavaScript strings are case-sensitive.

      `'Triangle'` and `'triangle'` are different strings, so `.includes()` does not treat them as a match.
    </Aside>

1. (📍 `Shape`) Fix the constructor so shape types are normalized to lowercase.

    ```diff lang="js" title="~/inclass/09/shapes.js"
      export function Shape(type) {
    -     this.type = type;
    +     this.type = type.toLowerCase();
          /**
           * Calculates the area of the shape.
           * @returns {number | undefined} The area, or undefined when dimensions are missing.
           */
    ```

    After this change, `new Shape('Triangle')` stores the type as `'triangle'`, so the supported-shape check and the area calculation can both work.

    <Aside type="caution" title="Method Name">
      In JavaScript, the string method is `.toLowerCase()`.

      The idea is "make this lowercase," but the method name needs to be written exactly as `.toLowerCase()`.
    </Aside>

Today's lesson introduces JavaScript modules as a way to split code into focused files. A module can keep some names private, export the names other files need, and import names from other modules.

JSDoc adds a second layer of communication. It does not change the runtime behaviour, but it helps describe functions, objects, parameters, and return values so the code is easier to use from another file.

<Aside type="note" title="Exercise Suggestion">
  Ask students to improve the `assignDimensions()` function so it does not have two exit points.

  Multiple exit points in one function can be a code smell. The early `return` is convenient today, but as a code base changes, that kind of structure can make it easier to skip later logic by accident.

  A useful refactor would keep one final exit point while still preventing unsupported shapes from receiving dimensions.
</Aside>

<Aside type="tip" title="Understanding JavaScript 👀">
  The key habit in this lesson is to ask which file owns each piece of code.

  If a value belongs inside one file, keep it private. If another file needs it, export it intentionally and import it by name.
</Aside>
