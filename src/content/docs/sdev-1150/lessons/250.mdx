## Lesson Focus

This lesson tests the neutral `<user-card>` custom element from the custom-element lessons. Unlike the previous unit-testing lesson, the goal is not to practice test-driven development. The component and service code are already present. The goal is to learn how to test browser-oriented behavior and how to keep tests deterministic when the app uses live random profile data from `https://randomuser.me`.

Use this demo to show:

- why DOM components need a browser-like test environment
- what JSDOM can test well and where it differs from a real browser
- how Vitest Browser Mode with the preview provider gives a small real-browser smoke test
- how to render a custom element in a test
- how to query Shadow DOM safely
- how to test properties, observed attributes, public methods, and events
- why `bubbles: true` and `composed: true` matter for events dispatched from a custom element
- how a Random User API response is mapped into the data shape expected by `<user-card>`
- why random/live API data should be stabilized in automated tests
- how `vi.stubGlobal('fetch', ...)` can replace a network call directly
- how MSW can mock the external HTTP request at the request boundary

### Testing Custom Elements (Web Components)

The component test file already has imports, deterministic test data, a `renderCard()` helper, and cleanup.

```js title="tests/user-card.test.js"
import { afterEach, describe, expect, it, vi } from 'vitest';
import '../src/user-card.js';
import { testUsers } from './mocks/random-user-fixtures.js';

const testUser = testUsers[0];

function renderCard(user = testUser) {
  const card = document.createElement('user-card');
  card.user = user;
  document.body.append(card);
  return card;
}

afterEach(() => {
  document.body.innerHTML = '';
  vi.unstubAllGlobals();
});
```

<Steps>
1. Start with the seed test. This proves that importing `../src/user-card.js` registered the element.

    ```js title="tests/user-card.test.js"
    describe('user-card', () => {
      it('registers the custom element', () => {
        // Arrange and Act
        const definition = customElements.get('user-card');

        // Assert
        expect(definition).toBeTypeOf('function');
      });
    });
    ```

1. Focus the first rendering test with `it.only`. Replace the matching `it.todo(...)` with this first naive attempt.

    ```js title="tests/user-card.test.js"

      // Arrange and Act

      // Assert
    ```

    This fails because the `<h2>` is inside the component's Shadow DOM, not in the regular document tree.

1. Fix the rendering test by querying `card.shadowRoot`.


    If the component owns a Shadow DOM, start from the element under test. Querying from `document` can accidentally test the page instead of the component.

    ```js title="tests/user-card.test.js"
      expect(image.getAttribute('src')).toBe('https://randomuser.me/api/portraits/men/75.jpg');
    ```

    ```js title="tests/user-card.test.js"
      card.user = testUsers[1];
    ```

    ```js title="tests/user-card.test.js"
      // Arrange

      const button = card.shadowRoot.querySelector('button');

      // Act
    ```

1. Add the observed attributes test. This checks the component from the HTML attribute side instead of the JavaScript property/method side.

    ```js title="tests/user-card.test.js"
    it('syncs observed attributes into component state', () => {
      // Arrange
      const card = renderCard();
      const image = card.shadowRoot.querySelector('img');

      // Act
      card.setAttribute('avatar', 'https://randomuser.me/api/portraits/men/32.jpg');
      card.setAttribute('followed', '');

      // Assert
      expect(image.getAttribute('src')).toBe('https://randomuser.me/api/portraits/men/32.jpg');
      expect(card.followed).toBe(true);
      expect(card.shadowRoot.querySelector('button').textContent).toBe('Following');
    });
    ```

1. Add the custom event test. Listen on `document.body` so the test proves the event bubbles out of the component.

    ```js title="tests/user-card.test.js"
    it('dispatches a bubbling and composed follow-change event', () => {
      // Arrange
      const card = renderCard();
      const listener = vi.fn();
      document.body.addEventListener('follow-change', listener);

      // Act
      card.shadowRoot.querySelector('button').click();

      // Assert
      expect(listener).toHaveBeenCalledTimes(1);
      const event = listener.mock.calls[0][0];
      expect(event.detail).toEqual({
        id: '2788dcba-54f4-4bc6-9233-a5da11845daa',
        followed: true,
      });
      expect(event.bubbles).toBe(true);
      expect(event.composed).toBe(true);
    });
    ```
</Steps>

<Aside type="tip" title="Component contract">
These tests are not checking every private line inside `UserCard`. They check the contract another developer can observe: DOM output, public properties and methods, reflected attributes, and events.
</Aside>

### Testing Service Calls with Mock Service Workers (MSW)

The service tests use deterministic fixtures. The fixture keeps the Random User API shape and the mapped `user-card` shape beside each other.

```js title="tests/mocks/random-user-fixtures.js"
export const randomUserApiUrl = 'https://randomuser.me/api/1.4/';

export const randomUserResponse = {
  results: [
    {
      name: { first: 'Clarence', last: 'James' },
      location: { city: 'Sunshine Coast', country: 'Australia' },
      email: 'clarence.james@example.com',
      login: { uuid: '2788dcba-54f4-4bc6-9233-a5da11845daa' },
      picture: { large: 'https://randomuser.me/api/portraits/men/75.jpg' },
      nat: 'AU',
    },
  ],
};
```

<Steps>
1. Start with the seed mapping test.

    ```js title="tests/profile-service.test.js"
    describe('profile service', () => {
      it('maps Random User API data into the user-card data shape', () => {
        // Arrange
        const randomUser = randomUserResponse.results[0];

        // Act
        const user = mapRandomUser(randomUser);

        // Assert
        expect(user).toEqual(testUsers[0]);
      });
    });
    ```

1. Focus the direct fetch-stub test with `it.only`.

    ```js title="tests/profile-service.test.js"
    it.only('can replace fetch with a stub during a test', async () => {
      // Arrange
      vi.stubGlobal('fetch', vi.fn(async () => ({
        ok: true,
        json: async () => ({ results: [randomUserResponse.results[0]] }),
      })));

      // Act
      const profiles = await fetchUserProfiles(1);

      // Assert
      expect(profiles).toEqual([testUsers[0]]);
      const requestUrl = fetch.mock.calls[0][0];
      expect(requestUrl.origin + requestUrl.pathname).toBe(randomUserApiUrl);
      expect(requestUrl.searchParams.get('results')).toBe('1');
      expect(requestUrl.searchParams.get('inc')).toBe('name,location,email,login,picture,nat');
    });
    ```

    <Aside title="Stub vs. request mock">
    `vi.stubGlobal()` is small and direct. It proves our function can work with a replaced `fetch`, but it does not feel much like an HTTP boundary. That is why we also use MSW.
    </Aside>

1. Review the MSW handler.

    ```js title="tests/mocks/handlers.js"
    import { http, HttpResponse } from 'msw';
    import { randomUserApiUrl, randomUserResponse } from './random-user-fixtures.js';

    export const handlers = [
      http.get(randomUserApiUrl, () => HttpResponse.json(randomUserResponse)),
    ];
    ```

1. Review the server setup. This runs before the tests and resets handlers after each test.

    ```js title="tests/setup-msw.js"
    import { afterAll, afterEach, beforeAll } from 'vitest';
    import { server } from './mocks/server.js';

    beforeAll(() => {
      server.listen({ onUnhandledRequest: 'error' });
    });

    afterEach(() => {
      server.resetHandlers();
    });

    afterAll(() => {
      server.close();
    });
    ```

    ```js title="tests/profile-service.test.js"

      // Act
      const profiles = await fetchUserProfiles();

      // Assert
      expect(profiles).toEqual(testUsers);
    });
    ```

1. Remove `.only` after the MSW success-path test passes.

    ```diff lang="js" title="tests/profile-service.test.js"

    + it('returns mapped profile data from a mocked Random User API response', async () => {
    ```

1. Add the MSW error-path test. This overrides the default handler only for this test.

    ```js title="tests/profile-service.test.js"
    it('throws when the mocked Random User API response is not ok', async () => {
      // Arrange
      server.use(
        http.get(randomUserApiUrl, () => new HttpResponse(null, { status: 503 })),
      );

      // Act
      const action = fetchUserProfiles();

      // Assert
      await expect(action).rejects.toThrow('Could not load random users.');
    });
    ```
</Steps>

<Aside type="tip" title="Deterministic data">
Random data is useful for demos because it looks realistic. Random data is risky for tests because the expected answer keeps moving. Our tests use fixtures and mocks so the expected answer stays fixed.
</Aside>

## Teaching Notes

JSDOM gives Vitest enough browser-like APIs to create elements, append them to the document, inspect Shadow DOM, dispatch events, and test many component behaviors quickly. It is not a complete browser engine. Layout, rendering, CSS visual behavior, and browser-specific interaction details may need Browser Mode or manual inspection.

Vitest Browser Mode runs tests in a browser context. For this course demo, use the preview provider because it avoids adding Playwright or WebDriverIO dependencies. Keep the Browser Mode test small: it is there to prove that the component can run in a real browser, not to duplicate every JSDOM assertion.

The Random User API is useful for a demo because it returns realistic profile data and photos. It is risky for automated tests because the data is random, the network can fail, and the third-party service can be slow or unavailable. That tension is the reason for deterministic fixtures, direct fetch stubs, and MSW request handlers.

`vi.stubGlobal('fetch', ...)` is the smallest way to replace one global dependency during a test. It is direct and easy to read, but it does not preserve the shape of a real request boundary very well.

MSW intercepts HTTP requests and returns controlled responses. In this lesson, MSW lets the profile service call the absolute Random User URL while the test receives a stable response. That keeps the test close to the way the app communicates without relying on the live service.
